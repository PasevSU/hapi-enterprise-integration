# Отчетни манифести (hash report)

Четири декларативни манифеста — едно и също доказателствено подреждане и **едно място**, където
може да влезе генерирано съдържание: слотът `generator` между `Cryptographic Timestamp START` и
`Cryptographic Timestamp STOP`.

| Манифест         | Обхват (`input_scope`) | Тип в отчета               | За какво                                                |
| ---------------- | ---------------------- | -------------------------- | ------------------------------------------------------- |
| `single.json`    | `single_file`          | `HASHREPORT_TYP_SINGLE`    | един файл (PDF получава и хешове на текста по страници) |
| `combo.json`     | `current_folder`       | `HASHREPORT_TYP_COMBO`     | една папка, само файловете в нея                        |
| `combo_all.json` | `recursive_folder`     | `HASHREPORT_TYP_COMBO_ALL` | една папка **и всички подпапки**                        |
| `volume.json`    | `recursive_folder`     | `HASHREPORT_TYP_VOLUME`    | една папка с произход на тома                           |

Рекурсията **никога не е подразбираща се**: `combo` остава само текущата папка, а `combo_all` и
`volume` слизат надолу по дървото.

## Ред на секциите

`identity` → `system` → `hashes`/`files` → `volume` → `user` → `file`/`files` → `timestamp` →
`start` → **слот `generator`** → `stop` → `legal` → `checksums`

Слотът е един и е заключен:

```json
{ "key": "generator", "block": "slot", "between": ["start", "stop"] }
```

Манифест, в който слотът липсва, е дублиран или е преместен, се отхвърля.

## START / STOP

Записите ползват полетата на генератора. Без реална TSA заявка стойностите казват
`not established — no TSA call in this run`; нищо не се измисля. `Processing Duration` стои **след**
STOP подписа, защото е локална мярка, а не TSA-заверено време.

## Целостта на текста е доказателството

Всеки отчет получава в footer-а `PAGE TEXT HASHES` за страницата и завършващо приложение
`WHOLE FILE TEXT CHECKSUMS` с единадесет алгоритъма. Стойностите се преизчисляват от самия файл —
не се приемат на доверие.

## Употреба

`index.json` изброява манифестите (id, тип, обхват, файл), за да не се сканира папката на сляпо.
Файловете са чисти данни: не съдържат TSA токени, сертификати, подписи и тайни.

## Отношение към `report-manifest.js`

Това са **две различни неща** и не се заменят едно друго:

| Какво          | Къде                                                  | Какво описва                                                                                                                          |
| -------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Тези манифести | `custom_components/hapi_enterprise/report_manifests/` | съдържанието на hash отчета — секции, доказателствен ред, слот `generator` между START и STOP                                         |
| Report Studio  | `hapi_enterprise/report-manifest.js`                  | оформлението на отчета като елементи (`title`, `text`, `table`, `hash-table`, …) със системни типове `rfc3161-start` / `rfc3161-stop` |

И двете спазват едно правило: START е първи, STOP е последен и всичко генерирано влиза между тях.

## Проверка

`tests/report-manifests.cjs` валидира файловете още в монорепото — преди да влязат в изданието:
точно един слот `generator` между START и STOP, изрична рекурсия, пълнота на `index.json` и
липса на токени/сертификати/тайни.

`index.json` пази и `sha256` на всеки манифест (върху текста с CRLF → LF), а
`tests/haoss-release.cjs` сверява, че издаденият файл е точно записаният. Така промяна в манифест
не може да мине тихо: редактираш файла → опресняваш `sha256` в индекса, иначе тестът пада с
„sha256 за &lt;файл&gt; не съвпада“.
